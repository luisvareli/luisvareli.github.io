A Playwright suite you can read

End-to-end, API and accessibility tests against a public demo shop. A sample project of my own, written the way I would write it for a client.

Read the code on GitHub See the pipeline runs

What it covers

27 tests in Playwright and TypeScript. The pipeline runs them on every change: 26 pass, and 1 is skipped because it needs credentials that are not in the repo.

API
Product, category and brand endpoints, with the response shape checked against a schema.
UI
Search and sort, cart, forms and guest checkout.
Mobile
The same checkout on a phone-sized screen.
Accessibility
An automated scan of the main pages, with known issues kept in a baseline so new ones stand out.

Choices I made

  • Expected values come from the API. A UI test asks the API what the price is and checks that the page shows it. When the demo data changes, the tests do not break for the wrong reason.
  • Page objects stay small. One per page, with only the actions the tests need.
  • The checkout test is split into named steps. A failed run tells you which step broke, not only which line.
  • There is a written strategy. It says what is tested, what is left out and why.

What it found

  • Two accessibility defects. Lists on the home page contain items that are not list items, and a button on the sign-in page has no name, so a screen reader says only "button".
  • An API inconsistency. A product carries its brand without the slug field that the brands endpoint returns.
  • A page that only fails in the pipeline. Opening the checkout by URL works on my machine and renders without its data in GitHub Actions. I have not found the cause yet. It is written down as open, and the tests go through the menu.
  • A lesson about timing. Scanning for accessibility before the page finished loading reported nothing. The scan now waits for the network to settle.

All six are in the findings document.
