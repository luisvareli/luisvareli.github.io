Work I can point to

From my job on an enterprise formulation platform used by chemical, food and pharmaceutical manufacturers, and from three sample projects of my own.

Finding out what a regression suite is worth

I went through 2,440 past test executions of a large regression suite. It had found 52 real defects, and 172 test cases were empty or could not be executed but still counted as coverage. The team got options for trimming it, each checked against past results.

One duplicated record behind a customer-blocking error

A save failed with a message that pointed the wrong way. I followed it into the database and found a single duplicated audit record breaking primary keys across about 25 stored procedures, confirmed it with an A/B test, and wrote up the fix.

A sample suite you can read

27 tests in Playwright and TypeScript against a public demo shop: guest checkout on desktop and phone sizes, API contracts, and an accessibility scan that found two real defects. It runs in GitHub Actions, and UI tests take their expected values from the API instead of hard-coding them.
Read the case study

Report tests that prove they can fail

66 tests for three financial reports on a sample ERP database in PostgreSQL. Expected values are recomputed from the raw rows, not re-queried. To check the tests themselves, I planted 14 realistic defects in the report SQL; the suite catches all 14, and the pipeline fails if one ever slips through.
Read the case study

An evaluation harness for AI output

41 tests around an assistant that triages support tickets. Every ticket runs five times, rewritten tickets must get the same decision, and a release gate compares each version with the last accepted one, ticket by ticket. Ten defective versions are each rejected by the check that matches the defect. The assistant is a rule-based stand-in, so the project shows the method, not results about a real model.

How a project goes

The same four steps, whatever the size.

  1. Read before testing

    I look at the app, the code if you share it, and what has broken before.

  2. Agree on the risks

    We pick what to test first by what would cost you money or trust, and what to leave out.

  3. Write and run

    Tests go into your repo in small pull requests you can review.

  4. Hand it over

    Pipeline running, strategy written down, and a call so your team can continue without me.
