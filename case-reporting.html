Report tests that prove they can fail

Automated tests for three financial reports on a sample ERP database. A sample project of my own: the schema, the data and the reports were written for it.

Read the code on GitHub See the pipeline runs

The problem

A report can look right and still be wrong. A join counts an invoice twice. A date filter drops the last day of the month. A total is off by a cent because tax was rounded in the wrong place. Nothing crashes, and nobody notices until the numbers stop matching accounting.

These defects do not show up in UI tests. You find them by checking the numbers against the data they came from.

What I built

66 tests in TypeScript and Vitest against PostgreSQL, for monthly sales, accounts receivable aging and inventory valuation. The suite runs in about 2 seconds.

Source integrity
Is the data itself consistent? Queries that return the offending rows for rules a constraint cannot express.
Reconciliation
Expected values are recomputed from the raw rows in TypeScript. They share no SQL with the reports, so a wrong join does not repeat itself in the check.
Control totals
The aging report must tie to three plain sums: invoiced, paid and credited.
Hand-checked cases
16 documents, each built to break one rule, with the expected value worked out by hand.
Boundaries
An invoice issued at 23:30 local time on the last day of the month. A payment on the cut-off date. Day 30 and day 31 past due.
Invariants
Buckets add up to the total. Four quarters add up to the year. The session time zone changes nothing.

How I know the tests work

Tests that pass prove little on their own. So I planted 14 defects in the report SQL, one at a time: small, realistic mistakes of the kind that pass a code review. The suite has to fail for each one. If a defect goes unnoticed, the command fails and so does the pipeline.

Limits

  • The reports were written for this project. It shows the method, not defects found in a real product.
  • The data set is small, so performance is out of scope.
  • The checks and the reports follow the same written rules. If a rule is wrong, both are wrong. On a real project I confirm the rules with accounting before writing tests.
